🤔 생각 열기

눈금이 하나도 없는 4리터 물통과 3리터 물통이 있습니다. 수돗물은 얼마든지 쓸 수 있고, 물을 버리는 것도 자유입니다. 이 두 통만으로 정확히 2리터를 만들어야 합니다.

“대충 반쯤 채우면 2리터”는 안 됩니다. 눈금이 없으니 정확히가 조건입니다. 어떻게 하면 될까요? 그리고 가장 적은 횟수는 몇 번일까요?

힌트 무엇을 적어 두면 생각이 정리될까?

머릿속으로만 굴리면 금방 헷갈립니다. 대신 두 통에 담긴 물의 양을 짝지어 적어 보세요. 처음은 (0, 0), 4리터 통을 가득 채우면 (4, 0), 그것을 3리터 통에 부으면 (1, 3)입니다.

이렇게 적는 순간 문제가 완전히 달라집니다. “물 붓기”가 “짝지은 숫자에서 짝지은 숫자로 옮겨 가기”가 되니까요. 그리고 옮겨 갈 수 있는 곳은 정해져 있습니다. 이제 이 문제는 미로에서 길 찾기와 같은 종류가 됩니다.

1

문제를 상태로 쪼개기

인공지능이 문제를 푸는 첫걸음은 문제를 기계가 다룰 수 있는 형태로 다시 쓰는 것입니다. 그 형태가 바로 상태와 연산자입니다.

📘 개념 · 상태

문제를 해결하는 과정에서 거쳐 가는 하나하나의 상황을 상태라고 한다. 문제가 주어진 시작 상황을 초기 상태, 문제를 해결한 마지막 상황을 목표 상태라고 한다.

상태를 적을 때 중요한 원칙이 하나 있습니다. 문제를 푸는 데 필요한 정보만 적는다는 것입니다. 물통 문제에서는 “두 통에 담긴 물의 양”만 있으면 됩니다. 통의 색깔, 수돗물의 온도, 지금이 몇 시인지는 답과 아무 상관이 없습니다. 그래서 상태를 (4리터 통의 물, 3리터 통의 물) 두 숫자로 적습니다. 이렇게 불필요한 것을 걷어내는 일을 추상화라고 합니다.

📘 개념 · 연산자

한 상태를 다른 상태로 바꾸는 행동을 연산자라고 한다. 연산자를 적용할 수 있는 조건과, 적용한 뒤에 어떤 상태가 되는지를 함께 정해야 한다.

물통 문제의 연산자는 여섯 개입니다.

물통 문제의 연산자 — 상태 (a, b)에서 a는 4리터 통, b는 3리터 통에 담긴 물
연산자뜻결과 상태예
4L 채우기4리터 통을 수돗물로 가득 채운다(4, b)(0,3) → (4,3)
3L 채우기3리터 통을 수돗물로 가득 채운다(a, 3)(1,0) → (1,3)
4L 비우기4리터 통의 물을 모두 버린다(0, b)(4,2) → (0,2)
3L 비우기3리터 통의 물을 모두 버린다(a, 0)(1,3) → (1,0)
4L → 3L3리터 통이 차거나 4리터 통이 빌 때까지 붓는다(a−t, b+t), t=min(a, 3−b)(4,0) → (1,3)
3L → 4L4리터 통이 차거나 3리터 통이 빌 때까지 붓는다(a+t, b−t), t=min(b, 4−a)(3,3) → (4,2)

탐색 문제를 정의하는 다섯 요소

어떤 문제든 아래 다섯 가지를 정하면 탐색 문제가 됩니다. 이 다섯 줄을 채우는 것이 인공지능 개발자가 가장 먼저 하는 일입니다.

탐색 문제의 정의 — 서로 전혀 달라 보이는 문제도 같은 다섯 칸으로 정리된다
요소물통 문제미로 길찾기8-퍼즐틱택토
상태(4L 통의 물, 3L 통의 물)지금 서 있는 칸의 좌표타일 8개의 배치판 9칸의 O·X 배치
초기 상태(0, 0)출발 칸섞어 놓은 배치빈 판
연산자채우기·비우기·붓기 6가지위·아래·왼·오른쪽 이동빈칸과 이웃 타일 맞바꾸기빈칸에 내 기호 놓기
목표 판정4L 통의 물 = 2도착 칸에 도달1~8이 순서대로 놓임같은 기호 3개가 한 줄
비용연산 1회 = 1한 칸 이동 = 1타일 1회 이동 = 1수 1회 = 1
⚠️ 목표는 ‘상태’가 아니라 ‘판정 조건’일 수 있다

물통 문제의 목표는 “4리터 통에 2리터”입니다. 그런데 이 조건을 만족하는 상태는 (2, 0), (2, 3) 등 여러 개입니다. 즉 목표는 딱 하나의 상태가 아니라 조건을 만족하는 상태들의 묶음일 수 있습니다. 그래서 프로그램에서는 목표를 “이 상태와 같은가?”가 아니라 “이 조건을 만족하는가?”로 판정합니다.

2

상태 공간 — 문제 전체의 지도

📘 개념 · 상태 공간

초기 상태와 목표 상태를 포함하여, 연산자를 적용해 나타날 수 있는 모든 상태의 집합을 상태 공간이라고 한다. 탐색은 상태 공간 안에서 초기 상태로부터 목표 상태에 이르는 경로를 찾는 일이다.

이 정의의 힘은 “문제 풀기”가 “길 찾기”로 바뀐다는 데 있습니다. 물통을 붓는 일, 타일을 미는 일, 다음 수를 두는 일이 모두 “점에서 점으로 옮겨 가기”가 됩니다. 문제의 겉모습은 사라지고 점과 선만 남습니다. 그래서 하나의 탐색 알고리즘을 만들어 두면 수많은 문제에 그대로 쓸 수 있습니다.

물통 문제의 상태 공간을 세어 봅시다. 4리터 통에는 0, 1, 2, 3, 4리터가 담길 수 있으니 5가지, 3리터 통에는 0, 1, 2, 3리터이니 4가지입니다. 곱하면 5 × 4 = 20가지입니다. 그런데 이 20가지 모두에 실제로 도달할 수 있을까요? 시뮬레이터로 직접 확인해 보면 재미있는 사실을 알게 됩니다. (0, 0)에서 출발해 여섯 연산자만 쓰면 14가지에만 도달할 수 있습니다. 나머지 6가지는 아무리 해도 만들 수 없습니다.

🔍 도달할 수 없는 상태가 있다는 뜻

상태 공간을 정의할 때는 “있을 수 있는 모든 상태”를 넣지만, 실제 탐색이 다루는 것은 초기 상태에서 연산자로 이어지는 부분뿐입니다. 예를 들어 (1, 1)은 두 통 모두 눈금이 없으므로 만들 방법이 없습니다. 이것은 인공지능에서 중요한 의미를 가집니다. 상태 공간이 아무리 커도 실제로 뒤져야 하는 부분은 그보다 작을 수 있다는 것입니다.

3

트리로 펼칠까, 그래프로 접을까

상태 공간을 눈으로 보기 좋게 그리는 방법은 두 가지입니다.

📘 개념 · 상태 공간 트리

초기 상태를 뿌리(루트)로 두고, 연산자를 적용해 만들어지는 상태를 자식으로 붙여 나무 모양으로 펼친 구조를 상태 공간 트리라고 한다. 여기서 상태는 노드로, 상태 사이의 관계(연산자)는 간선으로 나타낸다.

트리로 펼치면 “어떤 순서로 뒤졌는지”가 한눈에 보입니다. 뿌리에서 아래로 내려간 칸 수가 곧 깊이이고, 그것이 사용한 연산자의 개수입니다. 아래 그림은 물통 문제를 깊이 2까지 펼친 것입니다.

그림에서 문제가 보입니다. (4, 3)이 두 번 나타났습니다. 같은 상태인데 트리에서는 서로 다른 노드가 된 것입니다. 트리로 펼치면 이런 중복이 계속 늘어납니다. 게다가 (4,0)에서 4L 비우기를 하면 (0,0)으로 되돌아가므로, 그대로 두면 같은 곳을 무한히 맴돌게 됩니다.

📘 개념 · 그래프와 방문 표시

같은 상태를 하나의 노드로 합쳐 그리면 그래프가 된다. 프로그램에서는 이미 확인한 상태를 기록해 두고 다시 확장하지 않는데, 이 기록을 방문 표시라고 한다.

🌳

트리로 볼 때

탐색이 진행된 순서와 경로가 그대로 드러납니다. 깊이가 곧 연산 횟수이므로 “몇 단계 만에 풀었는가”를 읽기 쉽습니다. 다만 같은 상태가 여러 번 나타나 노드 수가 부풀어 오릅니다.

🕸️

그래프로 볼 때

같은 상태가 하나로 합쳐져 문제의 전체 구조가 보입니다. 어떤 상태가 서로 이어져 있는지, 도달할 수 없는 곳이 있는지 알 수 있습니다. 대신 방문 표시를 관리해야 합니다.

✅ 방문 표시가 없으면 어떻게 되는가

물통 문제에서 “4L 채우기 → 4L 비우기 → 4L 채우기 → …”를 반복하면 (0,0)과 (4,0) 사이를 영원히 왕복합니다. 방문 표시를 하면 두 번째로 (0,0)을 만났을 때 “이미 봤다”며 버립니다. 그래서 방문 표시는 단순한 최적화가 아니라 탐색이 끝나게 만드는 장치입니다.

4

왜 똑똑한 탐색이 필요한가 — 조합 폭발

물통 문제의 상태 공간은 20가지뿐이었습니다. 컴퓨터에게는 우스운 크기죠. 그러면 “모든 상태를 다 확인하면 되지 않나?”라는 생각이 듭니다. 이 생각이 왜 무너지는지 계산해 봅시다.

어떤 상태에서 적용할 수 있는 연산자의 개수를 분기 수(b)라 하고, 초기 상태에서 목표까지 필요한 연산 횟수를 깊이(d)라고 합니다. 그러면 깊이 d까지 펼친 상태 공간 트리의 노드 수는 다음과 같습니다.

📐 노드 수의 합

1 + b + b2 + b3 + ⋯ + bd

마지막 층 bd 하나가 그 위 모든 층의 합보다 크다는 점이 핵심이다.

📘 개념 · 조합 폭발

깊이가 하나 깊어질 때마다 확인해야 하는 상태의 수가 b배로 늘어나 걷잡을 수 없이 커지는 현상을 조합 폭발이라고 한다.

숫자로 느껴 봅시다. 분기 수가 10이라면 깊이 1에서 10개, 깊이 5에서 10만 개, 깊이 10에서 100억 개가 됩니다. 1초에 100만 개를 확인하는 컴퓨터라도 깊이 10을 다 훑으려면 세 시간 가까이 걸립니다. 그런데 실제 문제의 분기 수는 10보다 훨씬 큽니다.

대표 문제의 대략적인 규모 — 자세한 환산은 아래 시뮬레이터에서 직접 확인한다
문제평균 분기 수 b평균 깊이 d규모
틱택토 (3×3)약 49서로 다른 판 5,478가지 · 끝까지 두는 경기 255,168가지
체스약 35약 80게임 트리 약 10120가지
바둑 (19×19)약 250약 150규칙에 맞는 판 약 2.1×10170가지
⚠️ 우주에 있는 원자보다 많다

관측 가능한 우주의 원자 수는 대략 1080개로 추정됩니다. 체스의 게임 트리는 10120가지, 바둑의 판은 10170가지입니다. 즉 모든 경우를 저장하는 것 자체가 물리적으로 불가능합니다. 컴퓨터가 더 빨라지기를 기다리는 것으로는 절대 해결되지 않습니다. 필요한 것은 속도가 아니라 “어디를 안 봐도 되는지 아는 능력”입니다.

그래서 인공지능의 탐색은 두 갈래로 갈라집니다. 목표까지의 거리 정보를 쓰지 않고 정해진 순서대로 훑는 맹목적 탐색(3차시)과, “목표는 아마 이쪽”이라는 추정을 이용해 유망한 쪽부터 보는 정보 이용 탐색(4차시)입니다. 조합 폭발이야말로 정보 이용 탐색이 존재하는 이유입니다.

실생활 문제를 상태 공간으로 바꾸기

연습이 필요합니다. 아래 네 문제를 상태와 연산자로 다시 써 보겠습니다. 각 칸을 읽고 “나라면 상태에 무엇을 넣을까”를 먼저 생각해 보세요.

🔍 상태 설계가 성능을 결정한다

같은 문제라도 상태를 어떻게 정하느냐에 따라 상태 공간의 크기가 크게 달라집니다. 예를 들어 등교 경로에서 상태를 “지금 서 있는 역”으로 잡으면 역의 개수만큼 상태가 생깁니다. 그런데 “지금까지 지나온 역들의 목록”으로 잡으면 상태 수가 조합 폭발을 일으킵니다. 두 상태 모두 문제를 풀 수는 있지만, 앞의 것이 압도적으로 효율적입니다.

좋은 상태를 고르는 요령은 하나입니다. “앞으로 어떻게 해야 할지 판단하는 데 꼭 필요한 정보만 남기기.” 등교 경로에서는 어디를 거쳐 왔는지가 아니라 지금 어디에 있는지만 알면 다음 행동을 정할 수 있습니다.

심화 왜 (1, 1)은 만들 수 없을까 — 최대공약수의 비밀

시뮬레이터를 아무리 눌러도 (1, 1)이나 (2, 2)에는 도달할 수 없습니다. 이유가 있습니다. 두 통 모두에 물이 조금씩 남으려면 붓는 도중에 멈춰야 하는데, 눈금이 없으니 붓기는 “한쪽이 비거나 다른 쪽이 찰 때까지”만 가능합니다. 그래서 붓기가 끝나면 반드시 한쪽은 비어 있거나 한쪽은 가득합니다. 채우기·비우기도 마찬가지죠. 결국 도달 가능한 상태는 a=0, a=4, b=0, b=3 중 하나를 만족하는 것들뿐입니다. 5×4=20 중 이 조건을 만족하는 것은 14가지이고, 정확히 시뮬레이터가 보여 주는 수입니다.

더 일반적인 결론도 있습니다. 용량이 m, n인 두 통으로 만들 수 있는 물의 양은 m과 n의 최대공약수의 배수뿐입니다. 4와 3의 최대공약수는 1이니 1, 2, 3, 4리터를 모두 만들 수 있습니다. 만약 통이 4리터와 2리터라면 최대공약수가 2이므로 1리터나 3리터는 절대 만들 수 없습니다. 상태 공간을 그려 보면 이런 성질이 눈에 보입니다.

코드 파이썬으로 쓴 물통 문제의 연산자와 최소 단계

상태를 튜플 (a, b)로 두면 연산자는 여섯 개의 함수가 됩니다. 너비 우선 탐색으로 최소 단계를 구하는 부분은 3차시에서 자세히 배웁니다.

from collections import deque

CAP = (4, 3)                 # 두 통의 용량

def neighbors(s):            # 연산자 6개를 적용한 결과
    a, b = s
    out = []
    out.append((CAP[0], b))                    # 4L 채우기
    out.append((a, CAP[1]))                    # 3L 채우기
    out.append((0, b))                         # 4L 비우기
    out.append((a, 0))                         # 3L 비우기
    t = min(a, CAP[1] - b); out.append((a - t, b + t))   # 4L -> 3L
    t = min(b, CAP[0] - a); out.append((a + t, b - t))   # 3L -> 4L
    return [x for x in out if x != s]          # 제자리 연산은 버림

def solve(goal_a=2):
    start = (0, 0)
    came = {start: None}                       # 방문 표시 + 경로 기록
    q = deque([start])
    while q:
        s = q.popleft()
        if s[0] == goal_a:                     # 목표 판정
            path = []
            while s is not None:
                path.append(s); s = came[s]
            return path[::-1]
        for n in neighbors(s):
            if n not in came:                  # 이미 본 상태는 건너뜀
                came[n] = s
                q.append(n)
    return None

print(solve())   # [(0,0), (0,3), (3,0), (3,3), (4,2), (0,2), (2,0)] → 6단계

came 사전이 방문 표시와 경로 기록을 동시에 맡고 있습니다. 이 사전이 없으면 (0,0)과 (4,0) 사이를 영원히 왕복합니다.

사례 조합 폭발과 마주친 실제 문제들
  • 순회 판매원 문제 — 도시 n개를 한 번씩 들르는 가장 짧은 경로를 찾는 문제입니다. 경우의 수가 n! 로 늘어나 도시가 20개만 되어도 모든 경로를 확인할 수 없습니다. 택배 배송 경로 계획이 바로 이 문제입니다.
  • 단백질 접힘 — 아미노산 사슬이 접히는 모양의 가능한 수가 천문학적입니다. 그래서 모두 계산하지 않고 학습한 모델로 유망한 모양을 예측하는 방식이 쓰입니다.
  • 시간표 편성 — 교실·교사·학급·교시의 조합이 폭발합니다. 실제 학교 시간표 프로그램은 모든 경우를 보지 않고 “겹치면 즉시 포기”하는 방식으로 가지를 잘라 냅니다.

공통 해법이 보입니다. 가능성이 없는 가지는 일찍 잘라 내고, 유망한 가지부터 본다. 이것이 다음 두 차시의 주제입니다.

연결 다음 차시로 — 어떤 순서로 뒤질 것인가
이 차시에서 우리는 문제를 상태 공간으로 바꾸는 법을 배웠습니다. 이제 지도는 손에 들었습니다. 남은 질문은 하나입니다. “이 넓은 지도를 어떤 순서로 뒤질 것인가?” 3차시에서는 목표의 방향을 전혀 모른 채 훑는 두 가지 방법 — 가까운 곳부터 넓게 퍼지는 너비 우선 탐색과 한 방향으로 끝까지 파고드는 깊이 우선 탐색 — 을 나란히 돌려 보며 비교합니다.
