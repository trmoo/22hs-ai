🤔 생각 열기

세 팀이 같은 문제를 풀었습니다. 발표 시간에 이렇게 말했습니다.

  • 가온 팀 — “정확도 0.68이 나왔습니다. 시간이 없어서 여기까지 했습니다.”
  • 나리 팀 — “정확도 0.94입니다! 데이터 전체로 정규화하고 테스트 데이터로도 학습시켰습니다.”
  • 다온 팀 — “처음 0.68에서 시작했는데, 틀린 사례 30개를 모아 보니 한 학년의 데이터만 유독 적었습니다. 그 학년 데이터를 더 모아 0.86이 되었습니다.”

여러분이 심사위원이라면 어느 팀에 가장 높은 점수를 주고 싶은가요? 그리고 그 이유는 무엇인가요?

힌트 점수보다 중요한 것
나리 팀의 0.94는 데이터 누출로 부풀려진 점수입니다. 다온 팀은 점수가 더 낮지만 왜 틀렸는지 찾아내고 그것을 고쳤습니다. 이 차시는 다온 팀이 한 일 — 평가 결과를 읽고 원인을 찾아 고치는 일 — 을 연습합니다.
1

평가는 끝이 아니라 개선의 시작

모델을 학습시키고 정확도를 재면 프로젝트가 끝난 것 같습니다. 하지만 성능 평가의 진짜 목적은 점수를 매기는 것이 아니라 무엇을 고쳐야 할지 알아내는 것입니다. 그래서 인공지능 개발은 한 줄로 끝나지 않고 개선 사이클을 돕니다.

이 사이클에서 가장 자주 건너뛰는 칸이 ②번입니다. 성능이 낮으면 곧바로 알고리즘을 바꾸거나 값을 조정하고 싶어집니다. 하지만 원인을 모르고 손을 대면 운에 맡기는 일이 됩니다. 시간은 한정되어 있으므로, 먼저 오류 분석을 해야 합니다.

📘 개념

개선 사이클은 평가 → 원인 분석 → 개선 → 재평가를 반복하는 과정이다. 한 바퀴에서는 한 가지만 바꾼다. 두 가지를 동시에 바꾸면 성능이 변했을 때 무엇 덕분인지 알 수 없어, 다음 바퀴에서 무엇을 해야 할지 판단할 근거가 사라진다.

2

무엇을 어떻게 틀렸나

정확도 0.68은 “100개 중 68개를 맞혔다”는 뜻일 뿐, 어떤 32개를 틀렸는지는 알려 주지 않습니다. 오류 분석의 첫걸음은 틀린 사례를 전부 꺼내어 눈으로 보는 것입니다. 30개 정도면 사람이 직접 훑어볼 수 있고, 대개 몇 가지 유형으로 뭉쳐 있습니다.

오류 목록을 유형별로 모아 본 예 — “진로 추천 모델”의 틀린 사례 32건
오류 유형건수추측되는 원인가장 알맞은 개선
2학년 학생을 계속 틀림142학년 데이터가 전체의 8%뿐2학년 데이터 더 수집
‘예술’ 계열을 ‘인문’으로 예측9두 계열을 구분할 속성이 없음새 속성 추가(특성 공학)
결측치가 많은 행에서 틀림6결측치를 0으로 채워 왜곡전처리 방법 개선
원인을 알 수 없음3–잠시 보류

이 표를 만들면 무엇부터 해야 할지가 저절로 드러납니다. 32건 중 14건이 한 학년에서 나왔으니, 알고리즘을 바꾸는 것보다 그 학년 데이터를 모으는 편이 훨씬 효과적입니다. 오류 분석은 시간이 드는 일이지만, 헛된 개선에 쓸 시간을 아껴 줍니다.

혼동 행렬을 다시 보기

분류 문제라면 혼동 행렬이 오류 분석의 가장 좋은 출발점입니다. 어느 칸에 오류가 몰려 있는지가 한눈에 보입니다.

혼동 행렬 — 감염병 자가진단 모델(테스트 200건). 가로가 예측, 세로가 실제이다.
예측: 양성예측: 음성합계
실제: 양성참양성 24거짓음성 1640
실제: 음성거짓양성 8참음성 152160
합계32168200

정확도는 (24+152)÷200 = 0.88로 꽤 좋아 보입니다. 그런데 양성이라 예측한 것 중 실제 양성의 비율인 정밀도는 24÷32 = 0.75, 실제 양성 중 찾아낸 비율인 재현율은 24÷40 = 0.60입니다. 감염자 10명 중 4명을 놓치고 있다는 뜻이니, 이 모델은 정확도만 보면 놓치는 문제를 안고 있습니다.

⚠️ 정확도 한 숫자만 보면 안 되는 이유

전체의 80%가 음성인 데이터에서 무조건 “음성”이라고만 답하는 모델도 정확도 0.80을 얻습니다. 아무것도 학습하지 않았는데도 말입니다. 그래서 개선 방향을 정할 때는 정확도 옆에 정밀도·재현율과 혼동 행렬을 반드시 함께 놓고 봅니다. 놓치면 큰 피해가 생기는 문제(질병, 사고)에서는 재현율을, 잘못 지목하면 피해가 큰 문제(스팸 차단, 부정 적발)에서는 정밀도를 더 중요하게 봅니다.

3

성능을 올리는 다섯 가지 길

원인을 찾았다면 이제 고칩니다. 성능을 올리는 방법은 크게 다섯 가지이고, 각각 드는 비용과 기대할 수 있는 효과가 다릅니다.

다섯 가지 개선 방법의 비용과 효과 — 효과는 “문제의 원인이 그것일 때”의 값이다.
방법구체적으로비용효과이럴 때 효과적
① 데이터를 더 모으기 표본 수를 늘리거나, 부족한 집단의 데이터를 집중해 모은다 매우 큼 (시간·사람) 보통 가장 큼 훈련·테스트 성능이 둘 다 낮을 때, 특정 집단에서만 오류가 몰릴 때
② 전처리를 개선하기 결측치 처리 방법을 바꾸고, 이상치를 걸러 내고, 정규화를 적용한다 작음 작음 ~ 큼 데이터가 지저분할 때, 거리 기반 모델에서 열마다 값의 범위가 크게 다를 때
③ 좋은 속성을 만들기 기존 열을 조합해 새 속성을 만든다 — 특성 공학 보통 큼 서로 다른 두 부류가 지금 속성으로는 겹쳐 보일 때
④ 알고리즘을 바꾸기 k-NN → 결정 트리 → 랜덤 포레스트 → 신경망 등으로 교체한다 보통 보통 데이터와 속성은 괜찮은데 모델이 관계를 표현하기에 너무 단순할 때
⑤ 하이퍼파라미터 조정 하이퍼파라미터인 k, 최대 깊이, 학습률 등을 여러 조합으로 시도한다 작음 (컴퓨터가 함) 보통 가장 작음 다른 것을 다 손본 뒤 마지막에 짜낼 때
✅ 기억할 순서

연구와 현장의 경험이 한결같이 가리키는 것은 데이터의 양과 질입니다. 같은 시간을 쓴다면 데이터 → 전처리 → 속성 → 알고리즘 → 하이퍼파라미터 순서로 손보는 것이 대체로 효율적입니다. 하이퍼파라미터 조정은 가장 손이 쉽게 가는 일이지만, 대개 마지막 몇 퍼센트를 짜내는 역할에 그칩니다.

훈련 성능과 테스트 성능을 따로 보기

어떤 길을 고를지는 두 성능의 관계가 알려 줍니다. 훈련 성능도 낮고 테스트 성능도 낮다면 모델이 아직 충분히 배우지 못한 것이므로, 속성을 늘리거나 더 유연한 알고리즘으로 바꿉니다. 반대로 훈련 성능은 높은데 테스트 성능이 낮다면 훈련 데이터를 외워 버린 과대적합이므로, 데이터를 늘리거나 모델을 단순하게 만들어야 합니다.

훈련 성능테스트 성능진단해야 할 일

0.980.69과대적합 — 외워 버렸다데이터 늘리기, 모델 단순화, 속성 줄이기

여러 모델의 예측을 모아 다수결이나 평균으로 결정하는 앙상블은 성능을 올리는 강력한 방법입니다. 다만 모델이 복잡해지므로, 데이터가 적을 때 쓰면 훈련 성능만 오르고 테스트 성능은 오히려 떨어질 수 있습니다.

4

성능만 좋으면 좋은 인공지능일까

정확도 0.92를 달성했다고 해서 좋은 인공지능 소프트웨어라고 할 수는 없습니다. 그 0.92가 누구에게 0.92인지, 틀린 8%가 누구에게 몰려 있는지, 그 예측이 어떻게 쓰일지를 함께 물어야 합니다. 개발을 마치기 전에 다섯 영역을 점검합니다.

프로젝트 평가 루브릭

인공지능 프로젝트는 완성된 소프트웨어 하나로만 평가하지 않습니다. 주제를 잘 골랐는지, 해결 방식이 창의적인지, 팀원과 어떻게 협력했는지, 윤리적 문제를 살폈는지를 루브릭으로 함께 봅니다. 아래 표를 읽고 지금 우리 팀이 어느 칸에 있는지 표시해 보세요.

인공지능 프로젝트 평가 루브릭 — 다섯 항목을 골고루 반영한다.
평가 항목A 매우 우수B 우수C 보통D 노력 필요
주제의 적절성 지속가능발전목표와의 연결이 분명하고, 인공지능으로 풀기에 알맞은 크기로 문제를 좁혔다 목표와의 연결이 분명하고 문제가 대체로 구체적이다 주제를 정했으나 인공지능으로 풀 수 있는 형태로 좁히지 못했다 주제가 막연하고 목표와의 연결을 설명하지 못했다
문제 해결 방식의 창의성 데이터·속성·접근 방법에서 남과 다른 시도를 하고 그 이유를 설명했다 배운 방법을 문제 상황에 맞게 응용했다 수업의 예시를 거의 그대로 따라 했다 해결 방법을 스스로 정하지 못했다
협업 역할을 나누고 중간에 서로 바꿔 보았으며, 변경 이유를 기록으로 남겼다 역할을 나누어 맡은 일을 끝내고 회의에 꾸준히 참여했다 맡은 일은 했으나 다른 역할의 진행 상황은 알지 못했다 참여가 드물어 팀 결과물에 기여하지 못했다
완성도 파이프라인이 처음부터 끝까지 오류 없이 동작하고, 성능을 수치와 근거로 제시했다 대체로 동작하며 성능을 수치로 제시했다 일부 단계가 동작하지 않아 결과를 얻지 못했다 코드가 실행되지 않는다
윤리적 고려 편향·프라이버시·오용 가능성을 점검하고 실제 조치를 취해 기록했다 점검표로 확인하고 개선할 점을 적었다 언급은 했으나 실제 점검은 하지 않았다 사회적 영향을 고려하지 않았다

심화 검증 데이터 — 테스트 데이터를 아껴 써야 하는 이유

개선 사이클을 돌 때마다 테스트 데이터로 성능을 재면, 조금씩 테스트 데이터에 맞춰 결정을 내리게 됩니다. 열 번쯤 반복하면 테스트 점수도 더 이상 “처음 보는 데이터”의 점수가 아닙니다.

그래서 실제로는 데이터를 훈련 · 검증 · 테스트 셋으로 나눕니다. 개선 방향은 검증 데이터로 판단하고, 테스트 데이터는 마지막에 딱 한 번만 씁니다. 데이터가 적으면 훈련 데이터를 다시 여러 겹으로 나눠 돌려 쓰는 교차 검증을 씁니다.

from sklearn.model_selection import cross_val_score

점수 = cross_val_score(model, X_train, y_train, cv=5)
print(점수.mean(), 점수.std())   # 평균과 흔들림을 함께 본다

사례 편향이 실제로 문제가 된 방식

과거에 여러 나라에서 보고된 사례들은 공통된 구조를 가집니다.

  • 채용 심사 모델 — 과거 합격자 데이터로 학습하니 과거의 성별 편중을 그대로 재현했습니다. 데이터가 과거의 관행을 담고 있었기 때문입니다.
  • 얼굴 인식 — 학습 데이터에 특정 피부색·성별의 사진이 적어, 그 집단에서 오류율이 몇 배 높게 나타났습니다.
  • 의료 자원 배분 모델 — “의료비 지출”을 건강 상태의 대리 지표로 썼더니, 병원에 덜 갈 수밖에 없던 집단이 건강하다고 판정되었습니다.

세 사례 모두 알고리즘의 결함이 아니라 데이터와 지표 선택의 문제였습니다. 그래서 점검은 코드가 아니라 데이터와 목표 설정에서 시작해야 합니다.

연결 단원을 마무리하며
1차시에서 지속가능발전목표에서 주제를 찾고, 2차시에서 계획을 세우고, 3차시에서 파이프라인을 조립해 소프트웨어를 만들고, 이번 차시에서 평가 결과로 성능을 개선했습니다. 이 네 차시를 한 문장으로 줄이면 이렇습니다 — 인공지능은 한 번에 완성되지 않고, 고치는 과정을 통해 완성된다. 단원 마무리에서 전체 과정을 하나의 개념 지도로 정리하고, 프로젝트 결과를 스스로 점검해 봅니다.
